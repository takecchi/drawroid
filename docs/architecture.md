この文書は [north_star.md](./north_star.md)（正典）と [PRD.md](./PRD.md)（要件）から導いた設計である。上位の文書と矛盾したら、上位の文書が勝つ。ここには「どう作るか」の骨格だけを書く。具体的には、境界・依存の向き・データの配置・不変条件である。要件と進捗は書かない。関数の単位の How はコードに置く（[AGENTS.md「情報の置き場所」](../AGENTS.md#情報の置き場所)）。

**〔初稿の提案〕** と印を付けた値と選択は、この初稿で提案するものであり、人間の確認を通るまでは確定ではない。印の付いた項目の一覧は [未解決事項](#未解決事項) の末尾にまとめる。

## 全体像

```
 ブラウザ（apps/web = React Router v7 の SPA。SWR でポーリング）
        │  HTTP（同一オリジン。画面は API しか持たない）
┌───────▼───────────────────────────── drawroid（単一の Node.js プロセス）──┐
│  Hono ─┬─ /api/*  … packages/api（全操作はここにある）                     │
│        └─ /*      … apps/web のビルド成果物（静的配信）                    │
│                                                                           │
│  ジョブ実行器（packages/core）                                             │
│   ├ 待ち行列 … 走らせるジョブは同時に1つ。生成は直列                         │
│   └ ループ: 考える → 生成 → 見る → 次へ（止める条件に当たるまで）            │
│        │ 入力の組み立て器（予算） │ 許可 → 出力スキーマ │ 止める判定         │
│        │                                                                  │
│   ┌────▼──────────┐   ┌──────────────────┐   ┌────────────────────────┐  │
│   │ LlmPort        │   │ ImageBackend     │   │ ストア（ジョブ・記憶・  │  │
│   │ = packages/llm │   │ = backend-forge  │   │ 設定）= storage-fs      │  │
│   │  （AI SDK）     │   │  (将来 -a1111 …) │   │                        │  │
│   └────┬──────────┘   └───────┬──────────┘   └──────────┬─────────────┘  │
└────────┼──────────────────────┼─────────────────────────┼────────────────┘
         ▼                      ▼                         ▼
  LLM（Ollama / LM Studio /  画像生成（Forge / A1111。    データディレクトリ
  OpenAI / Anthropic）        多くは同じマシンの別プロセス） （~/.drawroid。ファイルのみ）
```

- 外にあるのは LLM と画像生成バックエンドだけである。Docker・DB サーバ・常駐の外部サービスは使わない。`drawroid` コマンド1つで、上の箱の全部が起動する。
- ループの中心（`packages/core`）は、provider もバックエンドの形もファイルの置き方も知らない。三方の外界とは、それぞれ core が定義するポートを通してだけ話す。
- 人間はループの外にいる。口出し・停止・選択は、API を通して「ファイルに書かれた出来事」としてループに届く。ループが人間を待つ箇所は無い。

## プロセスと待ち行列

- **単一プロセス。** API・Web UI の配信・ジョブ実行器が同じプロセスにある。
- **走らせるジョブは同時に1つ。** バックエンドの GPU は1枚と仮定するので、生成は直列になる。初稿では、1つのジョブの1回（考える→生成→見る）を丸ごと直列に回す。あるジョブの「考える」と別のジョブの「生成」を重ねて回すことはしない（[未解決事項](#未解決事項)）。
- **待ち行列は索引ファイルを持たない。** 起動時と各ジョブの終了時に `jobs/*/state.json` を走査し、`queued` のジョブをジョブ ID の順（＝作成順。下の [ジョブ ID](#データディレクトリの構造)）に並べる。

### ジョブの状態

```
queued ──▶ running ──▶ stopped（理由: ai / limit:iterations / limit:duration / limit:images / human / error）
   │                       ▲
   └──── human ────────────┘   （待ち行列にいる間も止められる）
```

止まった理由は `state.json` に、理由の種類と短い説明の両方で残す。`error` のときは、どの段で何が起きたか（スキーマ検証の再試行が尽きた・バックエンドに繋がらない、など）を書く。

### 再開 — 段単位

- **段の完了は、その段の出力ファイルがあることで決まる。** `think.json` があれば「考える」は済んでいる。生成した画像と `request.json` があれば「生成」は済んでいる。`judge.json` があれば「見る」は済んでいる。
- 起動すると、`running` のまま残ったジョブを、出力ファイルの無い最初の段から再開する。途中だった LLM の呼び出しと生成はやり直す。書き込みは原子的なので（[データディレクトリ](#データディレクトリの構造)）、半端な出力ファイルは存在しない。
- `state.json` に置くのは、持ち回す状態の要約とジョブの状態である。「どの段まで済んだか」は出力ファイルの有無が正であり、`state.json` にその写しを持たない（二重に持てばずれる）。

## ループの骨格

1回（イテレーション）は次の4段である。各段の出力をファイルに書き終えてから、次の段へ進む。

| 段 | 入力 | 出力（ファイル） |
|---|---|---|
| 考える | 持ち回す状態・未反映の口出し・記憶の抜粋・許可された候補（すべて予算内） | `think.json`: 許可されたパラメータだけの決定・短い理由・（口出しがあれば）更新した依頼の要点 |
| 生成 | `think.json` と「固定」の値 | `request.json`（バックエンドへ渡した中立の要求）・画像・バックエンドのメタデータ |
| 見る | 依頼の要点・参照画像の要点・記憶の抜粋・**今回の画像の縮小版（初めて渡すもの）**・最良候補の評価（テキスト） | `judge.json`: 画像ごとの点数と問題点・次に変えるべきこと・止めてよいか |
| 次へ | `judge.json`・止める条件 | `state.json` の更新（最良候補・直近の評価）。止めるか、次の回へ進むか |

### 持ち回す状態（要約）

`state.json` の `carry` が、回をまたいで LLM に渡る唯一の材料である。

| 欄 | 中身 | 誰が更新するか |
|---|---|---|
| 依頼の要点 | 依頼と、取り込んだ口出しを統合した意図。文字数の上限付き | 考える役（`think.json` の要点の欄。口出しを取り込んだ回だけ） |
| 参照画像の要点 | 参照画像ごとの短いテキスト | 見る役（参照画像が届いたときに1度だけ） |
| 最良候補 | どの回のどの画像か・点数・評価の短文 | 決定的な処理（点数の比較） |
| 直近の評価 | 前の回の `judge.json` の短い欄だけ | 決定的な処理 |
| 進み具合 | 回の番号・止める条件の残り（残りの回数・時間・枚数） | 決定的な処理 |

**不変条件:** 欄の数は固定で、どの欄にも上限がある。だから回数を何回重ねても `carry` の大きさは一定以下に収まる。過去の回の `think.json` / `judge.json` は、ファイルと UI にだけ残り、LLM には渡らない。

### 口出しの取り込み

- 口出しは届いた時点で `interventions/` に書く。走行中の段には触れない（生成中の1枚は止めない）。
- 次の「考える」の入力には、**未反映の口出しの原文**を載せる（1件あたりと合計に上限がある）。考える役は、それを依頼の要点へ統合した新しい要点を出力する。統合した口出しには「何回目で取り込んだか」を書き戻し、以後は LLM に渡さない。
- 予算に入りきらなかった口出しは捨てない。未反映のまま次の回へ回し、そのことを記録に残す。
- 止める条件の変更とマスクも口出しの一種である。止める条件の変更は、次の回の境目で `job.json` の止める条件へ反映する（LLM を通さない）。マスクは、それがあるあいだ inpaint を選択肢に加える（[許可の設定](#許可の設定)）。
- 依頼の要点を更新するのに、専用の LLM 呼び出しは足さない。考える役の出力の1欄で済ませる。

## パッケージ構成

```
apps/cli              `drawroid` コマンド。設定を解決し、各パッケージを組み立て（合成の根）、
                      Hono で packages/api と apps/web の成果物を配信する
apps/web              Web UI。React Router v7 の SPA（ssr: false）。packages/swr 経由で API だけを見る
packages/core         ループ・ジョブ実行器・持ち回す状態・入力の組み立て器と予算・
                      許可から出力スキーマを組み立てる処理・止める判定・記憶の選択と蒸留の手順。
                      ポート（LlmPort / ImageBackend / 各ストア）とドメインの型（zod）を定義する。
                      provider・バックエンド・ファイルの置き方を知らない
packages/llm          LlmPort の実装。AI SDK で provider を吸収する
packages/backend-forge  ImageBackend の Forge アダプタ（M6 で packages/backend-a1111 を足す）
packages/storage-fs   各ストアのファイル実装（データディレクトリの構造・原子的書き込み・画像の縮小版）
packages/api          Hono のルート。core の操作を HTTP に写すだけ。型（AppType）を書き出す
packages/swr          Web UI から API を叩く層（hono/client と SWR の hooks）
packages/ui           Web UI の見た目の部品。API を知らない
```

〔初稿の提案〕パッケージの名前は、この表を正とする。

依存の向き（矢印は「依存する」）:

```
apps/cli ─▶ packages/api ─▶ packages/core ◀─ packages/llm
   │                            ▲  ▲
   ├──────▶ packages/storage-fs ┘  └─ packages/backend-forge
   └──────▶ packages/llm, packages/backend-forge（組み立てるため）

apps/web ─▶ packages/swr ─▶ packages/api（型だけ）
        └─▶ packages/ui
```

- `packages/core` は、ほかのどのパッケージにも依存しない。AI SDK も Hono も Node の `fs` も import しない。
- アダプタ（`llm`・`backend-*`・`storage-fs`）は core が定義したポートを実装する。core 以外の兄弟には依存しない。
- 「どのアダプタを使うか」を決めるのは `apps/cli` だけである。

## データディレクトリの構造

〔初稿の提案〕既定は `~/.drawroid`。`DRAWROID_HOME` と CLI 引数（`--data-dir`）で変えられる。

```
~/.drawroid/
  config.json                 設定（全体の既定）。下「設定」
  candidate-notes.json        LoRA 等に人間が付けた短い説明（候補の名前 → 説明）
  memory/
    <memoryId>.md             記憶の1項目（front matter 付きの Markdown）。下「記憶」
  llm-calls/

  jobs/
    <jobId>/
      job.json                依頼の原文・止める条件・許可の上書き・バックエンドの指定
      state.json              ジョブの状態・止まった理由・持ち回す状態（carry）
      refs/
        <refId>.<ext>         人間が添えた参照画像（原寸）
        <refId>.json          用途の言葉・要点のテキスト・LLM に渡した呼び出しの ID
      masks/
        <maskId>.png          人間が塗った inpaint のマスク
      interventions/
        <seq>.json            口出し（原文・添付・マスク・止める条件の変更・取り込んだ回）
      iterations/
        0001/
          think.json          考える役の決定
          request.json        バックエンドへ渡した中立の要求（「固定」の値を当てたあと）
          images/
            <n>.png           生成された画像（原寸）
            <n>.json          バックエンドの応答のメタデータ（実際の seed など）
            <n>.preview-<長辺>.webp   LLM に渡す縮小版
            <n>.sent.json     この画像を LLM に渡した呼び出しの ID（渡した印）
          judge.json          見る役の評価
      selections/
        <imageKey>.json       お気に入り・却下
      distill.json            ジョブ終了時の蒸留で記憶に加えた・直した項目
      llm-calls/
        <callId>.json         このジョブの LLM 呼び出しの記録
```

不変条件:

- **ファイルの配置そのものが正である。** 索引ファイルは持たない。ジョブの一覧は `jobs/` の readdir、回の一覧は `iterations/` の readdir で得る。`jobs/<jobId>/` を消せば、そのジョブは消える。
- **ジョブ ID と回のディレクトリ名は、名前の順がそのまま時間の順になる形にする。** ジョブ ID は作成時刻を先頭に置いた形（〔初稿の提案〕例: `20261009-153012-k3f9`）、回は0埋めの番号とする。
- **書き込みは原子的に行う。** 同じディレクトリの一時ファイル（`.tmp-` 始まり）に書き、rename する。一時ファイルは読み手が無視し、起動時に片付ける。画像を先に置き、それを参照する JSON を後に置く（参照先の無い JSON を作らない）。
- **秘密はジョブの下に書かない。** API キーが置かれうるのは `config.json` だけである（下「設定」）。
- 人間が読める形にする。JSON は整形して書き、記憶は Markdown で書く。

## バックエンドのポート

Forge → A1111 → ComfyUI を差し替えられる境界である。core が型を定義し、`packages/backend-*` が実装する。

```ts
interface ImageBackend {
  probe(): Promise<BackendCapabilities>; // 繋がるか・使える機能と、使えない理由
  listCandidates(kind: CandidateKind): Promise<Candidate[]>; // checkpoint / vae / lora / sampler / scheduler / controlnet …
  generate(req: GenerationRequest, signal: AbortSignal): Promise<GenerationResult>;
  interrupt(): Promise<void>; // 走っている生成をバックエンド側で止める
}
```

- **`GenerationRequest` は中立の型である。** プロンプト・ネガティブ・チェックポイント・VAE・LoRA（名前と重み）・サンプラー・スケジューラ・ステップ・CFG・seed・解像度・Hires. fix・バッチ枚数・img2img（元画像と denoising strength）・inpaint（マスク）・ControlNet を、バックエンドを問わない形で持つ。元画像・マスクは、データディレクトリ内の参照で渡す。
- **バックエンド固有の形はアダプタの中に閉じる。** たとえば Forge / A1111 で LoRA をプロンプトの `<lora:名前:重み>` で指定するのは、アダプタが `request` から組み立てる。core はプロンプトに LoRA の構文を書かない。エンドポイント・フィールド名・ControlNet や inpaint の引数の形も、アダプタの外に出さない。
- **`BackendCapabilities` が、使えないものとその理由を持つ。** 拡張が無い、などである。core は、使えないパラメータを「使わない」と同じに扱って選択肢から外す。理由は API を通して UI に出す。
- **停止は2本立てで行う。** 人間が止めたら、`generate` に渡した `signal` を abort し、同時に `interrupt()` を呼ぶ。HTTP の待ちを切るだけでは、バックエンドの GPU は回り続けるからである。
- 接続先の URL は設定で決める。繋がらない・URL が違うときは、`probe` / `generate` が、原因の分かる種類のエラーを返す。

## AI SDK の境界

LLM 呼び出しは AI SDK を使う。provider ごとの差は `packages/llm` の中で吸収し、core には次の1つの口だけを見せる。

```ts
interface LlmPort {
  generateStructured<T>(call: {
    role: 'think' | 'judge';
    purpose: 'think' | 'judge' | 'ref-gist' | 'stop-parse' | 'distill';
    schema: ZodType<T>;
    messages: BudgetedMessages; // 組み立て器が作ったもの（下「予算」）。画像は縮小版の参照
    signal: AbortSignal;
  }): Promise<LlmCallOutcome<T>>; // 値 or 失敗理由 ＋ 試行ごとの生の出力・usage・所要時間
}
```

- **役割からモデルを解決する。** 設定の `roles.think` / `roles.judge` が provider とモデルを指す。既定では、見る役は考える役と同じモデルを使う。provider は少なくとも OpenAI 互換（Ollama・LM Studio・llama.cpp server 等）・OpenAI・Anthropic である。
- **構造化出力は必ず検証する。** モデルごとの出し方（ネイティブの JSON Schema・JSON モード・テキストから取り出す）は、役割の設定で選ぶ。どの出し方でも、最後に core のスキーマ（zod）で検証する。
  - 検証に失敗したら再試行する。再試行の入力に足すのは、直前の検証エラーの短い要約だけである（失敗した出力の全文は積まない）。
  - 回数が尽きたら失敗を返し、core はジョブを `error`（理由付き）で止める。検証を外す経路は作らない。
- **能力差は設定と検出で扱う。** 画像入力・構造化出力の方式・コンテキスト長は役割ごとに設定する。見る役に画像入力の無いモデルが指定されて呼び出しが失敗したら、理由付きで止める。
- **測る。** 試行ごとに、入力・出力のトークン数（provider が返す usage）と所要時間を返す。usage を返さない provider では「不明」と記録し、文字数は必ず記録する。記録のファイルを書くのは core である（[止める・見える](#止める見える)）。
- **秘密を外に出さない。** API キーは `packages/llm` の中でだけ使う。LLM 呼び出しの記録・ログ・API の応答には載せない。
- `signal` は AI SDK の呼び出しへそのまま渡す。人間が止めたら、走っている LLM の呼び出しを abort する。

## LLM への入力の予算

[north_star の原則2](./north_star.md#3つの原則このプロダクトの憲法) と、「立ち戻るための問い」の2つめ・3つめに答える節である。

### 組み立て器が唯一の入口

- LLM への入力は、用途ごとの組み立て器（`buildThinkInput` / `buildJudgeInput` / `buildRefGistInput` / `buildStopParseInput` / `buildDistillInput`）だけが作る。どれも core にある純粋な関数である。
- `LlmPort` が受け取るのは、組み立て器の戻り値の型（`BudgetedMessages`）だけである。別の経路で文字列を組んで渡すことは、型の上でできない。
- 組み立て器は、入力と一緒に「予算で落としたもの・持ち越したもの」の一覧を返す。この一覧は LLM 呼び出しの記録に載る。

### 予算の構造

〔初稿の提案〕予算の値はこの文書では決めない。実装のときに、設定（`config.json` の `budgets`）の既定値として決める。ここで決めるのは構造である。

| 予算 | 単位 | 締めるもの |
|---|---|---|
| 欄ごとの上限 | 文字数 | 依頼の要点・参照画像の要点・最良候補・直近の評価・口出し（1件と合計）・記憶の抜粋・候補の説明 |
| 件数の上限 | 件 | 口出し・記憶・候補（種類ごと）・参照画像の要点 |
| 画像 | 長辺 px・枚数 | 縮小版の長辺・1回の呼び出しに載せる画像の枚数（見る役。バッチの枚数の上限もこれに従う） |
| 全体 | トークン（見積もり） | 役割ごとのコンテキスト長（設定しなければ provider が報告する値。読めなければ既定値）から、出力の分を引いた残り |
| 出力 | トークン | 最大出力トークン（役割に設定したときだけ送る。設定しなければ provider 側の上限に任せ、全体の予算からは既定の分を引く）。出力の欄には文字数の上限を付けず、次の入力に載せるときに欄ごとの上限で切る |

- **全体の上限は、欄ごとの上限の和で守る。** 欄ごとの上限の和が全体を超える設定は、起動時と設定の保存時に検出して知らせる。
- 全体の見積もりでも溢れるときは、決めた順に欄を削り、削ったことを記録する。削る順は〔初稿の提案〕候補の説明 → 記憶 → 参照画像の要点 → 口出し（持ち越し）とし、依頼の要点は削らない。
- **出力も締める。** スキーマは短い欄の集まりにし、思考の垂れ流しを求める欄は置かない。欄に文字数の上限は付けない（超えた出力を落とすとジョブが止まるため）。長い出力が回を重ねて膨らまないことは、入力に載せるときの欄ごとの上限で守る。機能を足すときは、システムプロンプトの指示文ではなく、スキーマの欄で表す。

### 画像は縮小して1度だけ

- LLM に渡すのは縮小版（`<n>.preview-<長辺>.webp`）だけである。縮小版は storage-fs が作る。長辺は設定の値であり、ファイル名に入れるので、設定を変えても古い縮小版と混ざらない。
- 画像を入力に載せられるのは組み立て器だけである。載せた画像には、呼び出しの ID を `<n>.sent.json` / `refs/<refId>.json` に書く（渡した印）。印のある画像を組み立て器は載せない。評価済みの画像は、以後 `judge.json` の短い欄（テキスト）で持ち回す。
- 参照画像は、届いたときに見る役へ1度だけ渡し（`ref-gist`）、要点のテキストを `carry` に入れる。

### テストで保証すること

- 回を N 回重ねたときに、考える役・見る役への入力が、1回目と同じ予算の内に収まること。口出しを何回しても、記憶が数百項目あっても、LoRA が数百個あっても同じである。
- 同じ画像が2回渡らないこと。渡る画像が縮小版であること。

組み立て器が純粋な関数なので、これらはスタブを使わずに、状態を入れて結果の大きさを見るだけで確かめられる。

## 止める・見える

[north_star の原則3](./north_star.md#3つの原則このプロダクトの憲法) と、「立ち戻るための問い」の1つめ・4つめに答える節である。

### 止める

- **止める条件**は `job.json` に構造化した形で持つ。中身は、AI の判断で止めるか（真偽）・回数の上限・経過時間の上限・生成枚数の上限である。どれを使うかはジョブごとに人間が決める。
- **人間はいつでも止められる。** これは止める条件の1つではなく、いつでも使える操作として置く（PRD「止める条件」は「2系統」と書いたうえで3つを並べている。ここでは、人間の停止は常にある、と読む）。
- 自然言語の止める条件は、考える役が構造化した形に変換する（`stop-parse`）。変換結果を API が返し、人間が確認・修正したものを付けてジョブを作る。ジョブは、人間が確認するまで作られない。確認が要るのはジョブを作るまでで、作ったあとのループが人間を待つことは無い。
- **止める判定の位置。** 人間の停止は即座に効く。それ以外の判定は、回の境目（「見る」の後）で、次の順に行う: 人間の停止 → エラー → AI の判断（有効なら `judge.json` の「止めてよい」）→ 上限（回数・枚数・時間）。経過時間の上限は境目で判定するので、走っている1回は最後まで回る。
- **人間が止めたときの伝わり方。** 走っているジョブは `AbortController` を1つ持つ。停止の API が来たら、それを abort する。これで LLM の呼び出しと `generate` が中断され、同時に `ImageBackend.interrupt()` を呼ぶ。中断された段の出力は書かれない（原子的書き込み）。最後に、`state.json` を `stopped(human)` にする。

### 見える

- **ファイルに書かれていない判断で、次の段へ進まない。** 考える役の決定・生成の要求と結果・見る役の評価・口出しの取り込み・止まった理由・予算で落としたもの、のすべてが、上の配置のどこかにある。
- **すべての LLM 呼び出しを記録する。** 記録に載せるのは、用途・役割・provider とモデル・入力（画像はファイルへの参照）・試行ごとの生の出力と検証の結果・入力と出力のトークン数・文字数・所要時間・予算の内訳と落としたもの、である。
- **画面は API の上に乗る。** Web UI は、ファイルを API を通して読むだけである。画面にしか無い操作は作らない。
- 口出しは `interventions/` に「人間の指示」として残し、AI の判断（`think.json` / `judge.json`）とは別の種類として API が返す。

## 許可の設定

[north_star の「何を AI に許すか」](./north_star.md#alteroid-との違い取り違えやすいもの) と、「立ち戻るための問い」の5つめに答える節である。

```ts
type Permission =
  | { mode: 'auto'; choices?: string[] } // AI に任せる（候補の絞り込み付き）
  | { mode: 'fixed'; value: unknown } // 人間が値を決める
  | { mode: 'off' }; // 使わない
type Permissions = Record<ParamKey, Permission>;
```

- **全体の既定（`config.json`）に、ジョブの上書き（`job.json`）を重ねたもの**が、そのジョブの許可である。
- 回ごとの実際の許可は、この許可にバックエンドの能力（使えないものは `off` と同じ扱い）と、マスクの有無（マスクが無ければ inpaint は `off` と同じ扱い）を重ねて決める。
- **出力スキーマは、回ごとの実際の許可から組み立てる。** `auto` のパラメータだけがスキーマに入る。`fixed` と `off` は、スキーマにそもそも存在しない。候補を持つパラメータ（チェックポイント・LoRA 等）は、**その回に LLM へ見せた候補だけ**の enum になる。見せていない候補は、選べない。
- **「固定」は生成の直前に当てる。** `think.json` から `request.json` を作るときに、`fixed` の値を上書きする。スキーマに無いので AI は返せないが、返したとしても値は変わらない。
- **候補の一覧は全件を流さない。** バックエンドから取った候補を、まず許可（`choices`）で絞り、そのあと件数・文字数の予算内に入れる。入れる順は〔初稿の提案〕人間の説明があるもの → 依頼の要点に名前やタグが現れるもの → 残り、とする。入りきらなかったものは記録に残す。
- 人間が付けた説明（`candidate-notes.json`）は、候補と一緒に、予算内で渡す。

## 記憶

「立ち戻るための問い」の8つめに答える節である。好みは記憶に置き、コードや固定のプロンプトに埋め込まない。

### 形

〔初稿の提案〕1項目1ファイル（`memory/<memoryId>.md`）で持つ。本文は好みを短く書いたもの（例:「指の崩れは許容しない」）。front matter には次を置く。

```yaml
---
tags: [anime, checkpoint]   # 選ぶときの手がかり
scope: always               # always = 常に候補 / tagged = タグが当たったときだけ
sources: [20261009-153012-k3f9]   # どのジョブから学んだか
createdAt: 2026-10-09T15:40:00+09:00
updatedAt: 2026-10-09T15:40:00+09:00
---
アニメ調はチェックポイント X を好む
```

- 人間がファイルを直接直しても、消しても、そのまま反映される。記憶は呼び出しのたびに読み直し、キャッシュを持たない。
- Web UI の閲覧・編集・削除は、API を通して同じファイルを読み書きする。

### 選び方 — LLM を使わない

〔初稿の提案〕依頼に関係する項目は、決定的な処理で選ぶ。選ぶためにトークンを使わない。

1. `scope: always` の項目と、`tags` のどれかが依頼の要点に現れる項目を集める。
2. 次の順で並べる: `always` → 当たったタグの数 → `updatedAt` の新しい順。
3. 件数・文字数の予算内に入るぶんだけ渡す。落とした項目は、LLM 呼び出しの記録に載せる。

考える役と見る役には、それぞれの予算で別々に選んで渡す。

### 蒸留

- ジョブが止まったときに、考える役が1回だけ行う（`distill`）。
- 入力は、依頼の要点（口出しは統合済み）・止まった理由・選択と却下（画像ではなく、その画像の評価の短い欄）・上の方法で選んだ既存の項目。どれも予算内に収める。
- 出力は「項目を足す / 既存の項目を直す」の操作の一覧である（スキーマで表す）。〔初稿の提案〕AI は項目を消さない。消すのは人間である。
- 加えた操作は、`distill.json` と各項目の `sources` に残す。これで、どのジョブから学んだかが辿れる。

## HTTP API と Web UI

〔初稿の提案〕待ち受けの既定は `127.0.0.1:7878`（Forge / A1111 の 7860・ComfyUI の 8188 と衝突しない）。ポートは CLI 引数（`--port`）で変えられる。待ち受けのアドレスは `127.0.0.1` に固定し、変える引数は置かない（PRD「スコープ外」に、公開サーバとしての運用がある）。

リソースの骨格（細部はコードと `packages/api` の型が正）:

| リソース | 操作 |
|---|---|
| `/api/health` | 起動の確認 |
| `/api/config` | 設定の読み書き（秘密は伏せて返す） |
| `/api/backend` | 能力（使えないものと理由）・候補の一覧・候補への説明の読み書き |
| `/api/stop-conditions/parse` | 自然言語の止める条件 → 構造化した形（ジョブを作らない） |
| `/api/jobs` | 一覧（走行中・待ち・終了）・作成（依頼・参照画像・止める条件・許可の上書き） |
| `/api/jobs/:id` | 詳細・停止・口出し（参照画像・マスク・止める条件の変更を含む） |
| `/api/jobs/:id/iterations` | 各回の決定・要求・画像・評価 |
| `/api/jobs/:id/selections` | お気に入り・却下 |
| `/api/jobs/:id/llm-calls`・`/api/llm-calls` | LLM 呼び出しの記録 |
| `/api/files/*` | データディレクトリ内の画像の配信（`jobs/` の下に限る） |
| `/api/memory` | 記憶の一覧・閲覧・編集・削除 |

- M1 の「パラメータを明示して1回生成する」は、〔初稿の提案〕回が1つだけの手動ジョブとして同じ配置に置く。生成の結果の置き場を2種類にしない。
- Web UI と API は同じオリジンから配信するので、CORS は要らない。更新は SWR のポーリングで反映する。

## 設定

- **置き場所は `<データディレクトリ>/config.json`。**
- **優先順位は、CLI 引数 > 環境変数 > `config.json` > 組み込みの既定値。** 〔初稿の提案〕環境変数は、データディレクトリの `DRAWROID_HOME` と、API キーを入れる変数だけにする。
- 中身は次のとおり。
  - LLM: provider の一覧と、役割（`think` / `judge`）ごとの provider・モデル・コンテキスト長・画像入力の有無・構造化出力の方式
  - バックエンド: 種類と URL
  - 許可の全体の既定
  - 予算
  - 再試行の回数
- **API キーは、環境変数の名前を指す形を推奨とし、`config.json` に直接書くこともできる。** どちらの場合も、`/api/config` は伏せて返し、ログと LLM 呼び出しの記録には載らない。

## 技術選定

| 領域 | 選定 | 理由 |
|---|---|---|
| ランタイム | Node.js 22 系（`mise.toml` で固定） | Node.js だけで起動する（PRD） |
| モノレポ | pnpm workspaces | alteroid に揃える |
| 言語・検査 | TypeScript（strict）・ESLint・Prettier | alteroid に揃える |
| テスト | Vitest | 同上 |
| HTTP | Hono | API と静的配信を1プロセスで行う。`hono/client` で Web UI と型を共有する |
| Web UI | React Router v7（SPA、`ssr: false`）・SWR | AGENTS.md「実装の前提」 |
| LLM | AI SDK（`ai` と provider パッケージ: OpenAI 互換・OpenAI・Anthropic） | provider を問わない。agent loop を自作しない |
| スキーマ | zod | 出力スキーマを許可から動的に組み立て、検証する |
| 画像の縮小 | 〔初稿の提案〕sharp | 縮小と webp 書き出し。ネイティブの依存なので、`npx` での導入に障らないかは M2 で確かめる |

## 未解決事項

- **ジョブの段を重ねて回すか。** 初稿では1つのジョブを丸ごと直列に回す。あるジョブが LLM を待っているあいだに、別のジョブの生成で GPU を使うかどうかは、M2 の実測（LLM と生成の所要時間の比）で見直す。
- **ジョブの終了後に付いた選択・却下を、記憶にどう入れるか。** 蒸留はジョブの終了時に1回行うので、そのあとの選択は入らない。選択のたびに小さく蒸留し直すか、次の蒸留でまとめて扱うかは、M5 で決める。
- **日本語の依頼とタグの照合の精度。** 決定的な選び方（部分文字列の一致）で足りるかは、M5 の実測で見直す。足りなくても、選ぶために LLM を使う前に、決定的な方法の改良を先に試す。
- **トークン数の見積もりの方法。** usage を返さない provider や、呼び出す前の見積もりに何を使うか（文字数からの換算か、tokenizer か）は、M2 で決める。
- **実機の確認の手順書の置き場所。** M1 で決める。
- **sharp を使うかどうか**（上の [技術選定](#技術選定)）。

### 初稿の提案の一覧（人間の確認待ち）

- 待ち受けの既定 `127.0.0.1:7878`、アドレスは固定
- データディレクトリの既定 `~/.drawroid`、`DRAWROID_HOME` と `--data-dir` で上書きする
- パッケージの名前と分け方（[パッケージ構成](#パッケージ構成)）

- 再開は段単位で、段の完了を出力ファイルの有無で決める
- 予算は構造だけを決め、値は実装のときに設定の既定値として決める。予算から溢れたときに削る順
- 候補を予算に入れる順
- ジョブ ID の形
- M1 の単発生成を、回が1つの手動ジョブとして置くこと
- 環境変数を `DRAWROID_HOME` と API キーに限ること
- 画像の縮小に sharp を使うこと
