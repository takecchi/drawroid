# 設計 — 会話するエージェントへの体験の方針変更

この文書は、オーナーが 2026-10-09 に示した体験（下の [目指す体験](#目指す体験)）に drawroid を移すための設計である。**正典（[north_star](../north_star.md)・[PRD](../PRD.md)・[milestones](../milestones.md)・[architecture](../architecture.md)）は書き換えていない。** 正典の改訂が要る所は [正典への改訂の提案](#正典への改訂の提案) に提案として置く。提案が正典に取り込まれるまでは、正典が勝つ。

決めきれない点は、推奨を採ったうえで [推奨で進める点](#推奨で進める点) に並べた。**どれも推奨で進める。変えるなら言ってほしい。**

## 目指す体験

オーナーの言葉の要旨:

- **セッションは会話ごとに分かれる。** 会話は保存され、あとから開き直して続きができる。記憶は会話をまたいで、ツールから呼べる
- **質問と指示を見分ける。** 「何ができますか？」「○○のキャラ描けますか？」は質問で、絵を描き始めない。後者なら、SD で何ができるかを調べるツールを呼んでから答える。「○○をしている○○を描いて」は指示なので、描き始める
- **描いている間のことが、チャットのログにリアルタイムで出る。** 「描きます」→ 生成の進み具合 → 画像 → 「これはちょっと違いますね」（品質の確認）→ また生成 …。**思考（thinking）の中身も出る**
- alteroid のように、**会話を開き直せて、SSE でリアルタイムに返ってくる**
- **いつでも中断でき、途中の画像に口を出せる。** 「チェック中です」の最中に「あ、これでいいから次はこうして」と割り込めば、AI はそれに従う

## 今の作りとの差

| 論点 | 今の main | 目指す体験 |
|---|---|---|
| 単位 | **ジョブ**（依頼1つ → 止める条件まで自律で回る）。`jobs/` だけがある | **会話**。その中で、指示が来たときにジョブが生まれる |
| 人間の入力の解釈 | 投入はすべて依頼。止める条件を自然言語から変換して、人間が確かめてからジョブを作る | 質問には答えるだけ。指示のときだけ描く |
| LLM の口 | `LlmPort.generateStructured` の1本。ストリームしない `generateText`。ツールの呼び出しと reasoning の取得は無い | テキストと思考の増分を流し、ツールを呼ぶ |
| 画面への届け方 | SWR のポーリング | SSE。途中で切れても再接続して続きを受け取る |
| 生成の進み具合 | 取る口が無い（`ImageBackend` に progress が無い） | 進み具合をログに出す |
| 口出し | `interventions/` に置き、次の回の「考える」で取り込む。走っている段には触れない | 評価の最中にも割り込める。「これでいい」で評価を打ち切り、次へ進む |
| 中断 | ジョブを丸ごと止める（abort ＋ `interrupt()`） | 会話のターンを止めることと、絵を止めることの両方ができる |

### alteroid から持ち込むもの・持ち込まないもの

alteroid の作り（読んだ範囲）:

- 会話は日誌に付く `conversationId` のラベルである。SDK のセッションはデーモン全体で1本だけで、会話ごとには分けていない
- SSE は `POST /chat`（投函してそのまま流す）と `GET /chat/:id/stream`（購読だけ）の2口ある。流すイベントは `queued`・`thinking`・`tool`・`text`・`ask_human`・`attachments`・`done`・`error`。15秒ごとのハートビートがある
- **`thinking` は「考えている」という合図だけで、中身を流さない。ツールについても名前だけを流し、引数と結果は流さない**
- 走行中のイベントはメモリに写しておく（`CloneProgress`）。写しを取ることと購読を張ることを、await を挟まない同じ同期区間で行う（`Clone#attach`）。これで取りこぼしも二重渡しも起きない。Last-Event-ID は使っていない。再起動のあとは、日誌に残った確定済みの発言だけが残る
- 走行中に人間が発言しても、ターンは止めない。発言は受信箱へ積み、次のターンでまとめて読む。中断は SDK の `Query.interrupt()` で行う

drawroid が持ち込むもの:

- 継ぎ目の保証（写しと購読を同じ同期区間で取る）
- `queued` と `thinking` を潰さない考え方
- ハートビート
- `clientMessageId` による二重送信の防止
- 人間がブラウザを閉じてもターンは走り続けること

drawroid が持ち込まないもの・変えるもの:

- **思考の中身・ツールの引数と結果を流す**（オーナーの要望。alteroid より見せる量が多い）
- **セッションを会話ごとに分ける**（オーナーの要望）。ただし SDK のセッションの resume のような「会話の全文を LLM 側に持ち続ける」形は採らない。drawroid はトークン最小が第一の制約なので（[north_star](../north_star.md#alteroid-との違い取り違えやすいもの)）、ターンごとに、予算内の入力を組み立て直す
- **イベントをファイルに確定させ、SSE の `id:` と Last-Event-ID で再接続する。** drawroid は単一プロセスでファイルに書くので、確定したイベントの列をそのまま再送の元にできる
- **走行中の発言で、LLM の出力を打ち切る**（[割り込み](#中断と割り込み)）。alteroid が止めないのは、上位モデルで掛かった分を捨てないためである。drawroid の主対象はローカル LLM なので、捨てる損より、人間を待たせない得の方が大きい

## 全体の形 — 会話の上の「話す役」と、その下で回るジョブ

```
 ブラウザ（会話の画面: ログ・入力欄・止めるボタン）
   │  POST 発言 / GET SSE（Last-Event-ID で再接続）
┌──▼──────────────────────────── drawroid（単一プロセス）──────────────────┐
│  会話の受け口（packages/api）                                             │
│   │                                                                      │
│  会話の実行器（packages/core/conversation）                               │
│   ├ ターン: 話す役の LLM がテキストを返す / ツールを呼ぶ（会話ごとに直列）    │
│   ├ ツール: 調べる・描く・直す・止める・選ぶ・記憶を引く/書く               │
│   └ ハブ: イベントを確定してファイルに書き、購読者へ流す（＋走行中の写し）   │
│        ▲ ジョブのイベントを橋渡し                                         │
│  ジョブ実行器（今の JobRunner。考える → 生成 → 見る）                      │
│   └ 回の段・画像・評価・止まった理由・生成の進み具合を、ハブへ出す           │
└──────────────────────────────────────────────────────────────────────────┘
```

**推奨（[推奨で進める点](#推奨で進める点) の1）: 今のジョブのループは残し、会話の層をその上に足す。** 話す役（新しい役割）は、人間と話し、ツールを選ぶ。絵の試行錯誤そのもの（考える → 生成 → 見る）は、今のジョブ実行器が今までどおり回す。そして、ジョブの各段を会話のログに AI の発言として出す。

- 「描きます」は、話す役が `start_drawing` を呼んだときの発言である
- 「これはちょっと違いますね」は、見る役の評価（`judge.json`）を会話のログに出したものである
- 「（SD 呼び出し）」の繰り返しは、ジョブの回である

画面の上では、オーナーの例のとおりに「AI がツールを呼びながら試行錯誤している」と読める。そのうえで、次の3つを保てる。

1. **原則1（ループは人間無しで回る）:** 指示を受けたら、ジョブは止める条件まで回り切る。話す役が毎回の判断を握る形にすると、話す役の1ターンの中でループを回すことになる。そうすると、1ターンのツール呼び出しと結果が積み上がる
2. **原則2（入力が回数に比例して増えない）:** 回をまたぐ材料は今の `carry` だけである。話す役は、回の中身を受け取らない。受け取るのはジョブの要約（`carry` の短い欄）だけである
3. **今の資産:** 予算・許可からの出力スキーマ・止める判定・再開・記憶の選び方は、今のまま使える

もう一方の案（話す役が、生成・評価を1回ずつツールとして呼ぶ「完全なエージェント」）を採らない理由は、[推奨で進める点](#推奨で進める点) の1に書いた。

## 会話（セッション）のモデル

### 単位

- **会話**は、人間と話す役との一続きのやりとりである。ID は時刻を先頭に置いた形にする（ジョブ ID と同じ形。例: `20261009-153012-k3f9`）
- **ターン**は、人間の発言1つ（またはまとめて読んだ数件）に対する、話す役の応答1回である。1ターンの中で、話す役はツールを何度か呼んでよい（上限は予算で決める）
- **会話ごとに、走るターンは同時に1本。** 別の会話のターンは並んで走ってよい。ただし、LLM と GPU は全体で取り合う（[同時に走るもの](#同時に走るもの)）
- **ジョブは会話に属してよい。** `job.json` に `conversationId` と、ジョブを作ったターンの番号を足す（省略可。今の投入画面と API で作ったジョブは、会話に属さない）
- **1つの会話で、走るジョブは同時に1つ。** 走っている間に新しく描く指示が来たら、話す役は `revise_drawing`（今のジョブを直す）か、`stop_drawing` のあと `start_drawing` のどちらかを選ぶ。2つ目の `start_drawing` は、ハーネスが断る。断った理由はツールの結果として返す

### 置き場所

今のデータディレクトリに `conversations/` を足す。配置そのものを正とし、索引を持たない不変条件はそのまま守る。

```
~/.drawroid/
  conversations/
    <conversationId>/
      conversation.json        タイトル（最初の発言から決定的に作る。人間が直せる）・作成時刻
      events/
        <seq>.json             確定したイベント1件（seq は0埋め。名前の順が起きた順）
      uploads/
        <uploadId>.<ext>       会話で人間が添えた画像（ジョブを作るときに refs/ へ写す）
      llm-calls/
        <callId>.json          話す役の LLM 呼び出しの記録（ジョブに属さないもの）
  jobs/<jobId>/                今のまま。job.json に conversationId が足されるだけ
  memory/                      今のまま。front matter の sources に会話 ID も入る
```

- **イベントは1件1ファイル**にする（[推奨で進める点](#推奨で進める点) の2）。同じディレクトリの一時ファイルに書いてから rename する、今の原子的な書き込みと同じ形で書ける。壊れた行の扱いが要らない。`seq` は、書き手（単一プロセスのハブ）が readdir の最大値＋1 で決める
- **ジョブの中身を会話へ写さない。** 画像・評価・考える役の決定は `jobs/` が正であり、会話のイベントは「どのジョブの何回目の何枚目か」の参照と、表示に要る短い欄だけを持つ。二重に持つと、ずれるからである
- `conversations/<id>/` を消せば、その会話は消える。会話に属していたジョブは消えない（ジョブの一覧にはそのまま残る）

### イベント（確定するもの）

ログの正本は `events/` である。画面の表示も、復帰も、話す役への入力の組み立ても、ここから行う。

| `type` | 中身 | 誰が書くか |
|---|---|---|
| `user.message` | 本文・添付の参照・`clientMessageId` | 受け口 |
| `turn.started` | ターン番号・まとめて読んだ発言の seq | 会話の実行器 |
| `assistant.reasoning` | 思考の本文（ステップごとに確定したもの） | 会話の実行器（話す役） |
| `assistant.message` | 本文（ステップごとに確定したもの）・打ち切られたかの印 | 会話の実行器（話す役） |
| `tool.call` | ツールの名前・引数・呼び出しの ID | 会話の実行器 |
| `tool.result` | 呼び出しの ID・結果の要約（表示用）・成否 | 会話の実行器 |
| `turn.ended` | 終わり方（`done` / `interrupted` / `error`）・理由 | 会話の実行器 |
| `job.started` | ジョブ ID・依頼の要点・止める条件・許可の要約 | 橋渡し |
| `job.think` | 回・考える役の思考（あれば）・決定の短い理由・変えたパラメータの要約・選択肢から外したもの（`plan.json`） | 橋渡し |
| `job.images` | 回・画像の参照（ジョブのファイル） | 橋渡し |
| `job.judge` | 回・画像ごとの点数と問題点・次に変えること・止めてよいか・見る役の思考（あれば） | 橋渡し |
| `job.intervention` | 取り込んだ口出し（どの回で取り込んだか） | 橋渡し |
| `job.stopped` | 止まった理由 | 橋渡し |

### イベント（確定しないもの）

次のものは**ファイルに書かない。** 増分ごとに書けば書き込みが数千回になり、確定したイベントと二重に持つことにもなる。

| `type` | 中身 |
|---|---|
| `delta.text` | 話す役の本文の増分 |
| `delta.reasoning` | 思考の増分（話す役・考える役・見る役のどれか、どのジョブのどの段か） |
| `generation.progress` | 進み具合（0〜1）・ステップ・残りの見込み時間・（設定で有効なら）途中の画像の参照 |
| `status` | `queued`（ターンの順番待ち）/ `waiting-llm`（LLM の最初の増分待ち）/ `job.paused`（人間の発言を聞くあいだ、ジョブを待たせている） |

- ハブは、走っている部品（いま流れている本文・思考・生成）の**写し**をメモリに持つ（alteroid の `CloneProgress` と同じ役目）。部品が確定してイベントになった時点で、その写しを捨てる
- プロセスが落ちれば写しは消える。確定していない本文は、復帰のあとに出ない（[再起動](#復帰)）

### 復帰

**画面を開き直したとき・接続が切れたとき:**

1. 画面は `GET /api/conversations/:id/events` で確定したイベントを読む（ページ単位。黙って打ち切らず、どこまで読んだかを返す）
2. 画面は `GET /api/conversations/:id/stream` を開き、最後に読んだ seq を `Last-Event-ID` で渡す
3. ハブは、継ぎ目で取りこぼしも二重渡しも起こさないように、次の順で流す（alteroid の `Clone#attach` と同じ考え方。ただしファイルの読み出しは非同期なので、購読を先に張る）
   1. 購読を張り、同じ同期区間で走っている部品の写しを取る。以後に届いたものは溜めておく
   2. 渡された seq より後の確定イベントをファイルから読み、流す
   3. 写しを流す
   4. 溜めたもののうち、2 で流した seq 以下の確定イベントを落として流し、以後は購読の分をそのまま流す
4. 確定イベントの SSE には `id: <seq>` を付ける。確定しないイベントには `id:` を付けない。ブラウザの `EventSource` は、切れると自分で再接続し、最後に受けた `id:` を `Last-Event-ID` で送る。だから、画面側で再接続を書かなくてよい

**プロセスが再起動したとき:**

- `turn.started` があるのに `turn.ended` が無いターンには、起動時に `turn.ended(interrupted, 理由: プロセスの再起動)` を書く。**ターンを自動ではやり直さない**（[推奨で進める点](#推奨で進める点) の8）。画面は、そのターンの発言に「送り直す」を出す
- ジョブは、今の段単位の再開で続きから回る。橋渡しも、再開した段から続けてイベントを書く
- 橋渡しが書き漏らしたイベント（段のファイルは書けたが、イベントを書く前に落ちたもの）は、ジョブの段のファイルとイベントの差から、起動時に書き足す。ジョブのファイルが正であり、イベントはその写しなので、差を埋めればよい

## 話す役 — ツールを呼ぶエージェント

### 役割

LLM の役割に `talk`（話す役）を足す。既定は考える役と同じモデルである。今の `think`・`judge` の設定（provider・モデル・コンテキスト長・画像入力・構造化出力の方式）に、次の2つを足す。

- `toolCalling`: `native`（モデルのツール呼び出しを使う）/ `json`（構造化出力で代える。[逃げ道](#ツールの呼び出しに弱いモデルの逃げ道)）
- `reasoning`: `native`（provider が返す reasoning を使う）/ `think-tag`（本文の `<think>…</think>` を思考として切り出す）/ `none`

### 質問と指示を見分ける

見分けるのは話す役である。専用の分類の呼び出しは足さない（呼び出しが1回増え、トークンを払うことになるため）。仕組みでは次の3つで支える。

- **描き始めるツールは1つだけ（`start_drawing`）。** 説明文に「人間が描くよう求めたときだけ呼ぶ。描けるかを聞かれたときは呼ばない」と書く。説明文はツールの定義に置き、システムプロンプトには足さない
- **調べるツールは副作用が無い。** 「描けますか？」に答えるために呼んでも、何も始まらない。迷ったら調べるツールを呼ぶ方が安全である
- **描き始めたことは、ログに必ず出る。** 誤って描き始めても、人間は止められる（原則3）。止めるボタン、または「まだ描かないで」と書けばよい

### ツール

| ツール | 中身 | 副作用 | 結果（話す役へ返すもの。予算内） |
|---|---|---|---|
| `describe_backend` | バックエンドの能力と、使えない機能とその理由 | なし | 短い一覧 |
| `search_candidates` | `kind`（checkpoint / lora / …）と検索語で、候補を引く。許可された候補だけを対象にする | なし | 当たった候補の名前と人間の説明。件数・文字数の予算内 |
| `recall_memory` | 検索語に関係する記憶を引く（今の決定的な選び方） | なし | 当たった項目。予算内 |
| `remember` | 好みを記憶に書く（「覚えておいて」と言われたとき） | 記憶の追加 | 書いた項目の ID |
| `start_drawing` | 依頼の要点・止める条件（省けば既定）・枚数・許可の絞り込み（下）でジョブを作る | ジョブの作成 | ジョブ ID・解決した止める条件 |
| `revise_drawing` | 走っているジョブへ指示を置く（今の口出し）。止める条件の変更も含む | 口出しの追加 | 受けた口出しの ID |
| `adopt_image` | ある回のある画像を「これでいい」として選ぶ。下の [中断と割り込み](#中断と割り込み) | 選択の記録と、その回の評価の打ち切り | 選んだ画像の参照 |
| `stop_drawing` | 走っているジョブを止める | 停止 | 止めた結果 |
| `drawing_status` | 会話のジョブの今の状態（回・最良候補の点数・止める条件の残り） | なし | `carry` の短い欄 |
| `review_image` | 指定した画像を見る役に評価させる（人間が「この絵どう？」と聞いたとき） | 見る役の呼び出し | 評価の短い欄 |

- **「生成状況を見る」ツールは、LLM が進み具合を見に行くためのものではない。** 進み具合はハーネスが SSE で画面へ直接流す（`generation.progress`）。LLM に進み具合を見に行かせると、待つたびにトークンを払うことになるからである。`drawing_status` は、人間に「今どう？」と聞かれたときに答えるためのツールである
- **許可は狭めることしかできない（[推奨で進める点](#推奨で進める点) の7）。** `start_drawing` の許可の欄で話す役ができるのは、人間の許可を狭めることだけである。つまり、`auto` を `off` にするか、`auto` を、その候補の中の値で `fixed` にするかである。広げる経路は無い。ハーネスが検証し、広げようとした呼び出しは失敗として返す。「LoRA は使わないで」と人間が言えば、話す役はこれで表せる
- **止める条件の確認を、投入の前に挟まない（[推奨で進める点](#推奨で進める点) の5）。** `start_drawing` の結果（解決した止める条件）は `tool.call` / `tool.result` としてログに出る。人間は「5回までにして」と言えば変えられる（`revise_drawing`）。止める条件を省いたときの既定は、設定に足す（例: AI の判断＋10回）
- 画像を添えた発言は、`start_drawing` / `revise_drawing` に、添付の参照を渡して参照画像にする（今の `refs/` に写す）

### ターンの入力（予算）

話す役への1回の入力は、次の欄だけで組み立てる。**会話の長さにも、ジョブの回数にも比例して増えない。**

| 欄 | 中身 | 上限 |
|---|---|---|
| システム | 短い役目の説明 | 固定 |
| ツールの定義 | 上の表（名前・説明・引数のスキーマ） | 固定 |
| 直近のやりとり | 直近 K 件の `user.message` と `assistant.message` の本文（1件ずつ文字数で切る） | 件数・文字数 |
| 会話のジョブ | 走っている（または直前に止まった）ジョブの `carry` の短い欄と、状態 | 文字数 |
| このターンのステップ | このターンで呼んだツールと、その結果の要約 | ステップ数・結果1件の文字数 |

- **思考を入力に戻さない。** 思考（`assistant.reasoning`・`job.think` / `job.judge` の思考）は、画面とファイルにだけ残す
- **古いやりとりは渡さない。** 直近 K 件より前は、渡さない（[推奨で進める点](#推奨で進める点) の9）。人間が「さっきの○○」と古い話を持ち出したときの備えは、ジョブの要点と記憶である
- **ツールの結果は、話す役へ返す前に予算で切る。** 切ったことは、LLM 呼び出しの記録に載せる（今の `BudgetReport` と同じ形）
- **1ターンのステップ数に上限を置く。** 上限に当たったら、話す役に「ここまで」と伝えて、最後の1ステップで返答させる。それでも返答が無ければ、ターンを `error` で閉じる
- 組み立て器は、今の `build*Input` と同じく core の純粋な関数（`buildTalkInput`）にし、`BudgetedMessages` を返す。**テストで保証すること:** 会話が 100 ターンあっても、ジョブが 30 回回っても、1回の入力が予算内に収まる

### LLM のポートの拡張

今の `LlmPort` に、ターン1回を流す口を足す。

```ts
interface LlmPort {
  describe(role: LlmRole): LlmRoleInfo;
  generateStructured<T>(call: LlmCall<T>): Promise<LlmCallOutcome<T>>;
  /** 話す役の1ステップ。増分を流し、最後にテキストかツールの呼び出しを返す */
  streamStep(call: TalkStepCall): AsyncIterable<TalkStepPart>;
}
type TalkStepPart =
  | { type: 'text-delta'; text: string }
  | { type: 'reasoning-delta'; text: string }
  | { type: 'tool-call'; callId: string; name: string; input: unknown } // 検証済み
  | { type: 'finish'; attempts: LlmAttempt[] }; // usage・所要時間・検証の失敗
```

- **ツールの実行は core が行う。** AI SDK の `streamText` にはツールの定義を渡す。ただし実行の関数は渡さず、1回に1ステップだけ回す。ステップをまたぐ繰り返しは core の会話の実行器が持つ。こうすれば、中断・予算・許可の検証・イベントの確定を、ステップの境目で core が決められる。AGENTS の「agent loop を自作しない」は、「LLM の呼び出しと構造化・ツールの解釈を自作しない」と読む。ステップの繰り返しは、ジョブのループと同じく、ハーネスの仕事である（[正典への改訂の提案](#正典への改訂の提案)）
- **今の `generateStructured` も、中ではストリームにする。** reasoning の増分を、呼び手に渡した `onReasoning` へ流す。こうすれば、考える役・見る役の思考もログにリアルタイムで出る。返り値の形は変えないので、ループの試験はそのまま通る
- provider ごとの差（reasoning の出し方・ツール呼び出しの形）は、今と同じく `packages/llm` の中で吸収する

## SSE

### 口

| 口 | 中身 |
|---|---|
| `GET /api/conversations` | 一覧（タイトル・最後の発言の先頭 80 字・走っているか） |
| `POST /api/conversations` | 作る |
| `PATCH /api/conversations/:id` | タイトルを直す |
| `GET /api/conversations/:id/events?after=<seq>` | 確定したイベント（ページ単位） |
| `GET /api/conversations/:id/stream` | SSE。`Last-Event-ID`（または `?after=`）から続きを流す |
| `POST /api/conversations/:id/messages` | 発言（本文・添付・`clientMessageId`）。202 と、確定した seq を返す。ストリームは返さない |
| `POST /api/conversations/:id/interrupt` | 中断。`scope: 'turn' \| 'all'`（下） |

- **発言の POST はストリームを返さない。** 流すのは GET の購読1本だけにする。こうすれば、画面はブラウザ標準の `EventSource` を使える。再接続と `Last-Event-ID` をブラウザが受け持つので、再接続を自前で書かなくてよい（alteroid は POST /chat で流すので `EventSource` を使えず、再接続を自前で書いている）
- **同じ `clientMessageId` の再送は、二重に受けない。** 2回目には、1回目の seq を返す
- 15秒ごとにハートビート（`: hb`）を送る。書き込みの失敗は握りつぶして、購読を外す
- 今の操作（ジョブ・口出し・選択・記憶・設定）の API は、そのまま残す。会話の画面も、画像の選択・マスク塗り・ジョブの詳細へのリンクには、今の API を使う。**画面にだけある経路は作らない**

### イベントの形

SSE の `event:` は `type`、`data:` は JSON（`type` も含む）にする。確定したイベントには `id: <seq>` を付ける。

```
id: 42
event: job.judge
data: {"type":"job.judge","seq":42,"at":"…","jobId":"…","iteration":3,"images":[{"index":0,"score":0.42,"issues":["手が崩れている"]}],"nextChange":"手を隠す構図に","canStop":false}

event: generation.progress
data: {"type":"generation.progress","jobId":"…","iteration":4,"progress":0.35,"step":7,"steps":20,"etaMs":5200}
```

確定しないイベントは、どの部品の増分かを `partId` で示す。部品が確定したときのイベントは、同じ `partId` を持つ。画面は、確定のイベントを受けたら、その部品の増分表示を確定の本文で置き換える。

## 生成の進み具合

- `ImageBackend` に、任意のメソッド `progress(signal): Promise<GenerationProgress | undefined>` を足す。Forge・A1111 のアダプタは `/sdapi/v1/progress` で実装する（進み具合・残り時間・ステップ・途中の画像）。持たないアダプタは実装しない。その場合、画面は「生成中」とだけ出す
- ジョブ実行器は、`generate` を待つ間、1秒ごとに `progress` を呼び、ハブへ `generation.progress` を出す。**LLM は通さない**
- 途中の画像は、既定では流さない（[推奨で進める点](#推奨で進める点) の13）。設定で有効にしたときだけ、途中の画像をメモリに1枚だけ持つ。SSE ではその URL（`/api/jobs/:id/progress-preview`）を流し、画像の中身は流さない
- 進み具合はファイルに書かない。生成が終われば `job.images` が確定する

## 中断と割り込み

### 人間が止める

`POST /api/conversations/:id/interrupt` で止める。

- `scope: 'turn'`: 話す役のターンを止める。走っている LLM の呼び出しを abort する。そこまで流れていた本文は `assistant.message`（打ち切りの印つき）として確定させ、`turn.ended(interrupted)` を書く。走っているツールは、終わるのを待つ（ツールはどれも短いので）。ジョブには触れない
- `scope: 'all'`: 上に加えて、会話のジョブを止める（今の `JobRunner.stop`。abort と `interrupt()`）
- 画面の「止める」ボタンは `all` を送る。オーナーの「中断を指示できる」は、絵も含めて止めることだと読む。「描くのは続けて」と言いたいときは、言葉で言えば話す役がそう扱う
- 「止めて」と言葉で言ったときは、話す役が `stop_drawing` を呼ぶ

### 話す役のターンの最中に、人間が発言したとき

**推奨（[推奨で進める点](#推奨で進める点) の3）: 走っているターンを打ち切り、新しいターンで、未読の発言をまとめて読む。**

- 流れていた本文と思考は、打ち切りの印を付けて確定させる。走っているツールは、終わるまで待つ（`start_drawing` が半分だけ走ることは無い）
- 新しいターンの入力には、直近のやりとりとして、打ち切った発言と新しい発言の両方が入る
- ただし、打ち切るのは LLM の出力を待っている間だけである。ツールの実行中は、ツールが終わってから打ち切る

### ジョブが走っている間に、人間が発言したとき

GPU と LLM は、全体で取り合う資源である。ローカル LLM のサーバは同時に1つしか捌けないことが多い。人間を待たせないために、次のように扱う（[推奨で進める点](#推奨で進める点) の4）。

| ジョブの段 | 扱い |
|---|---|
| 生成中（GPU） | 止めない（今の PRD どおり）。話す役のターンは、生成と並んで走る |
| 考える・見る（LLM） | **段の LLM 呼び出しを abort して、ジョブを境目で待たせる。** 話す役のターンが終わったら、ジョブは待ちを解いて、その段をやり直す（今の段単位の再開と同じく、出力ファイルが無い段からやり直す） |

- 待たせるのは人間の発言が来たときだけで、ターンが終われば必ず解ける。ターンが失敗しても、打ち切られても解ける。**人間を待って止まる形ではない**（原則1）
- 待たせている間、`status: job.paused`（確定しない）を流し、画面に「話を聞いています」と出す

**オーナーの例「チェック中です」→「これでいいから次はこうして」:**

1. 人間の発言が来る。見る役の呼び出しを abort し、ジョブを待たせる
2. 話す役のターンが始まる。話す役は `adopt_image`（その回の画像を選ぶ）と `revise_drawing`（次の指示）を呼び、「わかりました」と返す
3. `adopt_image` は、次の2つを行う
   - 画像をお気に入りにする（今の `selections/`）
   - その回の評価を「人間が選んだ」で打ち切る。`judge.json` の代わりに `adopted.json` を書き、段を済ませる。その画像を最良候補（`carry.best`）にし、点数は 1 として扱う。止める判定は、このあと人間の指示が続くので行わない
4. ターンが終わる。ジョブは待ちを解いて次の回の「考える」に入り、`revise_drawing` の指示を取り込む。前の回の画像を元にした img2img も、許可されていれば選べる

`adopt_image` だけで、次の指示が無いとき（「これでいい」だけ）は、ジョブを止める（止まった理由に「人間が選んだ」を足す）。

## 思考の表示

- **見せるのは、モデルが自分で出す思考だけである。** 思考を出させる指示や欄は足さない（AGENTS の地雷「思考の垂れ流しを出させる」は守る）。reasoning を出すモデルを選んだときに、その中身を捨てずに見せる、という変更である
- 思考は**入力に戻さない。** 次の呼び出しには、構造化した短い欄だけを持ち回す（原則2）
- 話す役・考える役・見る役の思考を、どれも `delta.reasoning` で流し、ステップや段が終わったら確定させる
- 画面では、流れている間は開いて見せ、確定したら畳む（クリックで開ける）
- 思考を出させないモデル設定（`reasoning: none`）では、何も出ない。出力トークンを減らしたい人は、モデルかサーバの側で思考を切ればよい（今の `cutAtLimitReason` の案内と同じ）

## ローカル LLM（OpenAI 互換）での扱い

### ツールの呼び出し

- `toolCalling: native` は、OpenAI 互換の `tools` / `tool_calls` を使う。llama.cpp server・LM Studio・Ollama・vLLM は、どれもこの形を受けるとされる。ただし、どのモデル・どのテンプレートで正しく出るかは、まちまちである
- ツールの呼び出しの引数は、core のスキーマで必ず検証する。合わなければ、検証エラーの要約だけを足して、同じステップをやり直す（今の構造化出力の再試行と同じ形。失敗した出力の全文は積まない）。回数が尽きたら、ターンを `error` で閉じ、理由をログに出す

### ツールの呼び出しに弱いモデルの逃げ道

`toolCalling: json` にすると、ツールの呼び出しを、今の構造化出力の口で代える。1ステップの出力を次のスキーマにする。

```ts
z.discriminatedUnion('kind', [
  z.object({ kind: z.literal('reply'), text: z.string() }),
  z.object({ kind: z.literal('tool'), name: z.literal('start_drawing'), input: startDrawingInput }),
  // … ツールごとに1つ。スキーマはツールの定義から組み立てる
]);
```

- 今の `structuredOutput`（`native` / `json` / `text`）の3通りが、そのまま使える。`text` のときは JSON Schema を指示文に載せ、本文から JSON を取り出す（今の `extractJson`）
- 本文の増分は、`reply.text` の部分的な JSON から取り出して流す（AI SDK の部分的なオブジェクトのストリーム）。取り出せない出し方のときは、確定してから一度に出す
- **それでも壊れるときの最後の逃げ道:** 検証の再試行が尽きたら、ツールを使わずに、話す役の生の本文を返答として出す。そのうえで「ツールを呼べなかった」とログに出し、ターンを `error` で閉じる。**描き始める・止める判断を、検証していない出力から推し量らない**（AGENTS の地雷「スキーマ検証を外す」）。人間は、今の投入画面からジョブを作れる（会話を経ない経路は残す）

### 思考

- `reasoning: native` は、AI SDK の provider が返す reasoning の部品を使う。OpenAI 互換のサーバは、思考を `reasoning_content` などの欄で返すことがある。それを AI SDK の OpenAI 互換 provider が reasoning として読むかは、**未確認である**（このリポジトリの AI SDK の版で、最初の段階で確かめる）
- `reasoning: think-tag` は、本文に `<think>…</think>` が混ざるモデル（Qwen 系など）のためのものである。AI SDK の reasoning を切り出すミドルウェアで、思考と本文を分ける
- `structuredOutput: native` と思考が両立しないサーバでは、`json` / `text` に落とす。これは今の設定の範囲で選べる

## 同時に走るもの

- **生成（GPU）は全体で直列。** 今の待ち行列のままである
- **ジョブの LLM の段と、話す役のターンは、重ならないようにする。** 人間の発言が来たら、ジョブの LLM の段を待たせる（上）。別の会話のターン同士は重なりうるが、人間は1人なので稀である。ローカル LLM のサーバが同時に捌けないときは、サーバの側で順に処理される
- **「待っている」と「考えている」を潰さない**（alteroid の `queued` と `thinking` を分ける考え方）。発言を受けてターンが始まるまでは `queued`、LLM の呼び出しを出してから最初の増分が来るまでは `waiting-llm`、増分が来てからが思考や本文である。どれも確定しないイベントとして流す
- 話す役のターンは、会話ごとに直列である

## 移行の段階

1段階 = 1つの PR を目安にした。それぞれ Issue に切れる粒度で書いてある。受け入れ条件は、どれもモック（スタブの LLM・スタブのバックエンド・一時ディレクトリ・AI SDK の試験用モデル）で確かめられる形にした。「実機で」と書いたものは、今の milestones と同じくオーナーが確かめる。

依存の向き: A → B → C、D は B の後、E は C・D の後、F は E の後、G・H・I・J は F の後なら順不同、K は最後。

### A. 会話の置き場所（core の型とポート・storage-fs）

- core に、会話・イベント（確定するもの）の型（zod）と、`ConversationStore` のポートを足す。storage-fs に、ファイルの実装を足す
- 受け入れ条件:
  - [ ] 会話を作り、イベントを足し、`after` の seq から読める（試験）
  - [ ] 書き込みの途中で失敗しても、壊れた JSON も、番号の欠けも残らない（一時ファイルで rename する試験）
  - [ ] `conversations/<id>/` を消せば一覧から消える（索引が無い）
  - [ ] `job.json` に `conversationId` が無いジョブを、今までどおり読める

### B. ハブ（走行中の写しと購読）

- core に、会話ごとのハブを足す。イベントを確定して書き、購読者へ流し、確定しない部品の写しを持つ
- 受け入れ条件:
  - [ ] 増分を流している最中に購読を張っても、取りこぼしも二重渡しも無い（増分の途中で購読し、受けた列を確かめる試験）
  - [ ] 部品が確定すると写しが消え、確定のイベントに同じ `partId` が付く
  - [ ] 購読者が書き込みに失敗しても、ほかの購読者と書き手に影響しない

### C. 会話の API と SSE

- packages/api に、[口](#口) の表の口を足す。ハートビートと `Last-Event-ID` の再送を入れる。この段階では、発言を受けて `user.message` を確定するだけにし、ターンはまだ走らせない
- 受け入れ条件:
  - [ ] SSE を読む試験で、確定したイベントに `id:` が付き、確定しないイベントには付かない
  - [ ] `Last-Event-ID: n` で繋ぐと、n より後だけが流れる
  - [ ] 同じ `clientMessageId` の再送で、イベントが1件しか増えない
  - [ ] ハートビートが既定の間隔で送られる（偽の時計で）
  - [ ] すべての口が HTTP の試験（`every-operation-over-http`）に載る

### D. LLM のポートの拡張（ストリーム・reasoning・ツール呼び出し）

- `LlmPort.streamStep` を足し、packages/llm で `streamText` によって実装する。`generateStructured` を中でストリームにし、`onReasoning` を受けるようにする。`ScriptedLlm` も `streamStep` に対応させる
- **最初に確かめること:** このリポジトリの AI SDK の版で、OpenAI 互換の provider が `reasoning_content` を reasoning として読むか。`<think>` を切り出すミドルウェアが使えるか。結果は PR に書く
- 受け入れ条件:
  - [ ] AI SDK の試験用モデルが流す本文・reasoning・ツール呼び出しが、`TalkStepPart` に写る
  - [ ] ツールの引数がスキーマに合わないとき、検証エラーの要約だけを足して再試行し、尽きたら失敗を返す
  - [ ] abort で、流れている呼び出しが止まる
  - [ ] `reasoning: think-tag` で、本文の `<think>` が思考に分かれる
  - [ ] `generateStructured` の返り値と、今のループの試験が変わらない
  - [ ] usage と所要時間がステップごとに記録される

### E. 話す役（副作用の無いツールだけ）

- core に、会話の実行器・`buildTalkInput`・副作用の無いツール（`describe_backend`・`search_candidates`・`recall_memory`・`drawing_status`）を足す。設定に `talk` の役割と予算を足す
- 受け入れ条件:
  - [ ] 台本の LLM で「何ができますか？」→ 本文だけを返し、ジョブが作られない
  - [ ] 「○○のキャラ描けますか？」→ `search_candidates` を呼び、その結果を使って答える。ジョブが作られない
  - [ ] 100 ターンの会話のあとでも、話す役への1回の入力が予算内に収まる（組み立て器の試験）
  - [ ] 思考が次の入力に含まれない
  - [ ] ツールの結果が予算で切られ、切ったことが記録に載る
  - [ ] ステップ数の上限で、ターンが返答で閉じる

### F. 描くツールとジョブの橋渡し

- `start_drawing`・`revise_drawing`・`stop_drawing` を足す。ジョブ実行器からハブへの橋渡し（`job.*` のイベント）を足す。許可の絞り込みの検証も、ここで入れる
- 受け入れ条件:
  - [ ] 「○○を描いて」→ `start_drawing` → 会話 ID 付きのジョブができ、`job.started` → `job.think` → `job.images` → `job.judge` → … → `job.stopped` の順にイベントが確定する
  - [ ] 許可を広げる引数（`off` を `auto` にする、候補にない値で `fixed` にする）は失敗として返り、ジョブが作られない
  - [ ] 走っているジョブがある会話で、2つ目の `start_drawing` が断られる
  - [ ] 止める条件を省くと、設定の既定が使われ、`tool.result` に解決した値が出る
  - [ ] `plan.json` で外したものが `job.think` に載る

### G. 会話の画面

- apps/web に、会話の一覧と会話の画面を足し、トップを会話にする。部品は、ログの行（人間・AI の本文・思考の折りたたみ・ツールのカード・生成のカード・画像と評価・止まった理由）・入力欄・止めるボタンである。購読は `EventSource` で行う
- 受け入れ条件:
  - [ ] 偽の `EventSource` から流したイベントで、各行が出る（部品の試験）
  - [ ] 思考は、流れている間は開き、確定したら畳まれる
  - [ ] 画面を開き直すと、確定したイベントからログが復元され、走っている部品の写しから続きが出る
  - [ ] 画像の行から、ジョブの詳細（今の画面）へ飛べ、お気に入り・却下ができる

### H. 生成の進み具合

- `ImageBackend.progress` を足し、Forge・A1111 のアダプタで実装する。ジョブ実行器で、生成の間それを呼び、`generation.progress` を出す
- 受け入れ条件:
  - [ ] HTTP のモックの `/sdapi/v1/progress` から、`generation.progress` が流れる
  - [ ] 生成が終われば止まり、ファイルに書かれない
  - [ ] `progress` を持たないバックエンドでも、ジョブが回る
  - [ ] 途中の画像は、設定で有効にしたときだけ URL が流れる
- 実機で: Forge で、進み具合が会話の画面に出る

### I. 中断と割り込み

- `POST /interrupt`（`turn` / `all`）を足す。走行中のターンへの発言で、ターンを打ち切って新しいターンにする。ジョブの LLM の段を待たせて、やり直す。`adopt_image` と、口出しの種類 `adopt`、`adopted.json`、止まった理由 `adopted` を足す
- 受け入れ条件（オーナーの例を台本にする）:
  - [ ] 見る役の呼び出しの最中に「これでいいから次はこうして」→ 見る役の呼び出しが abort される → 話す役が `adopt_image` と `revise_drawing` を呼ぶ → 画像がお気に入りになる → その回は `adopted.json` で済む → 次の回の「考える」に指示が入る
  - [ ] 生成中の発言では、生成が止まらない
  - [ ] 話す役のターンの最中の発言で、流れていた本文が打ち切りの印つきで確定し、新しいターンが両方の発言を読む
  - [ ] ツールの実行中に来た発言では、ツールが終わってから打ち切る
  - [ ] 話す役のターンが失敗しても、ジョブの待ちが解ける
  - [ ] `scope: all` で、ジョブも止まる（abort と `interrupt()`）
  - [ ] 「これでいい」だけなら、ジョブが `adopted` で止まる

### J. ツールの呼び出しに弱いモデルの逃げ道・思考の表示の仕上げ

- `toolCalling: json` を足す。考える役・見る役の思考を `job.think` / `job.judge` に載せ、`delta.reasoning` で流す
- 受け入れ条件:
  - [ ] `toolCalling: json` と `structuredOutput: text` の台本で、`native` と同じイベントの列になる
  - [ ] 壊れた出力が続いたら、生の本文を出して `error` で閉じ、ジョブを作らない
  - [ ] 考える役・見る役の思考が流れ、確定し、次の入力には入らない
- 実機で: ローカル LLM（OpenAI 互換）で、質問 → 調べる → 描く → 割り込む、が会話の画面で回る

### K. 復帰の仕上げと記憶

- 起動時の処理（閉じていないターンの `interrupted`、橋渡しの書き漏らしの補い）を足す。`remember` ツール、記憶の `sources` への会話 ID、蒸留の材料への会話の発言を足す
- 受け入れ条件:
  - [ ] ターンの途中でプロセスを落として起動すると、そのターンが `interrupted` で閉じ、画面に「送り直す」が出る
  - [ ] ジョブの段のファイルはあるのにイベントが無い状態で起動すると、イベントが補われる
  - [ ] 「覚えておいて」→ `remember` → 記憶のファイルができ、`sources` に会話 ID が入る。別の会話の `recall_memory` で引ける
  - [ ] 蒸留の入力が、会話の長さによらず予算内に収まる

## 推奨で進める点

**どれも推奨で進める。変えるなら言ってほしい。**

1. **ジョブのループを残すか、話す役が1回ずつ生成・評価を回すか** — 推奨: 残す（上の [全体の形](#全体の形--会話の上の話す役とその下で回るジョブ)）
   - 選択肢 A（推奨）: 話す役は会話とツールの選択だけを行い、試行錯誤はジョブが回す。帰結:
     - 原則1・2と今の資産がそのまま生きる
     - 話す役が「回ごとに作戦を変える」ことはしない。それは考える役の仕事のまま残る
     - 画面の上では、AI が回ごとに発言しているように見える
   - 選択肢 B: 生成・評価を話す役のツールにする。帰結:
     - 1ターンの中でツールの結果が回の数だけ積み上がる。原則2を守るには、ターンの中での要約や圧縮が要る
     - ツール呼び出しの弱いローカルモデルでは、ループが途中で止まりやすい
     - 今の `carry`・止める判定・段単位の再開の作り直しが要る
2. **イベントの置き方** — 推奨: 1件1ファイル（`events/<seq>.json`）
   - 帰結: 今の原子的な書き込みの規則をそのまま守れる。会話が長くなるとファイルの数が増える（数百〜数千。手元のツールなので許容する）
   - 選択肢: JSONL に追記する。ファイルは1つで済むが、末尾が壊れた行の扱いが要り、原子的な書き込みの規則から外れる
3. **話す役のターン中の発言** — 推奨: 打ち切って、まとめて読み直す
   - 帰結: 人間を待たせない。打ち切った分の出力トークンは捨てる
   - 選択肢: alteroid のように、積んで次のターンで読む。捨てる分は無いが、長い返答の間、人間が待たされる
4. **ジョブの LLM の段の最中の発言** — 推奨: 段を abort して待たせ、ターンのあとでやり直す
   - 帰結: 割り込みへの応答が速い。やり直す段の分のトークンを払い直す
   - 選択肢 a: 並べて走らせる。ローカル LLM のサーバが詰まり、両方遅くなる
   - 選択肢 b: 段が終わるまで待つ。見る役が終わるまで、人間が待たされる
5. **止める条件の確認** — 推奨: 投入の前には確認せず、ログに出して、言葉で直せるようにする
   - 帰結: 会話の流れを止めない。PRD の「変換結果を確認してから開始」の改訂が要る（下）。今の投入画面は今のまま確認する
6. **評価の言い回し** — 推奨: 見る役の短い欄（点数・問題点・次に変えること）を、画面が決まった型で文にする。見る役に「人間向けの一言」の欄を足さない
   - 帰結: 出力トークンが増えない。言い回しは機械的になる。思考を出すモデルなら、思考の表示が「AI がどう見たか」を補う
7. **話す役の許可の扱い** — 推奨: 狭めることだけを許し、広げる経路を作らない
   - 帰結: north_star の問い5を守れる。「LoRA を使わないで」は言葉だけで効く。「この LoRA を使って」は、人間が許可していなければ効かず、話す役はそう答える
8. **再起動で途切れたターン** — 推奨: `interrupted` で閉じ、自動ではやり直さない
   - 帰結: `start_drawing` の二重実行が起きない。人間は「送り直す」を押す
9. **話す役に渡す会話の長さ** — 推奨: 直近 K 件だけにし、LLM による要約は、今は足さない
   - 帰結: 呼び出しが増えない。古い話は忘れるが、ジョブの要点と記憶が残る。足りないと分かったら、要約の欄を `carry` と同じ「固定の欄・上限付き」で足す
10. **話す役のモデル** — 推奨: 既定は考える役と同じ
11. **思考の表示** — 推奨: 既定で表示する。モデルが出さなければ何も出ない
12. **今の投入画面** — 推奨: 残す。会話を経ずに細かく指定したいとき、そしてツールの呼び出しが壊れるモデルの逃げ道として使う
13. **生成の途中の画像** — 推奨: 既定では流さず、進み具合（割合・ステップ・残り時間）だけを出す
    - 帰結: 1秒ごとに画像を取って配る負荷が無い。設定で有効にできる
14. **会話の終わりの蒸留** — 推奨: 今は足さない。蒸留はジョブが止まったときだけとし、明示の「覚えておいて」は `remember` で受ける
